# 指示違反への診断と再指示

Sunoの生成結果が指示から外れたとき、「モデルが無視した」とだけ結論づけず、入力・設定・モデル特性・生成結果を分けて診断する。

## 症状が報告された後の応答原則

ユーザーが「既にサビ始まりを指定しているのにイントロが付く」「Rockを指定しているのに低音が薄い」と報告した場合、入力ミスだけに還元せず、生成後の症状に対する有益な改善案を先に出す。ただし、Lyrics全体やすべてのタグを妥当と仮定してはいけない。症状ごとに、確認の明快さと結果への影響で切り分けの深さを変える。

| 確認の種類 | 例 | 応答での扱い |
| --- | --- | --- |
| 明快で低コスト | サビ始まりなのにイントロが付く場合、`[Chorus]`より前に`[Intro]`、本文、instrumental cueがないか | 本質的な対策を示した後に、一文で確認する。Lyrics全体の監査へ広げない。 |
| タグ固有の確認 | `[Verse 1]`、`[Drop]`、長い角括弧指示など | そのタグだけを台帳で分類し、公式旧世代参照・コミュニティcue・未知・配置不備を確認する。妥当とも無効とも一括断定しない。 |
| 音楽的な診断 | 中域不足、低音不足、音が薄い | 楽器編成や役割を複数仮説に分け、単一のStyleを決め打ちしない。 |

応答の基本順序は次のとおり。

1. まず症状に対する再指示、設定変更、編成候補など、ユーザーが試せる改善案を提示する。
2. 次に、結果を変えうる確認を症状に必要な範囲だけ添える。
3. 音域や厚みの問題で編成が不明なら、2〜4案を提示する。各案には「何を前に出すか」「どの音楽的役割を追加するか」「どんな場合に近いか」を添える。
4. ユーザーが案を選ぶか「その他」を示した後に、貼り付け用Styleを確定する。

確認を省略しないが、確認だけで回答を終えない。電源コードの確認は一文で済む場合があり、回路設計の説明が必要な場合まで同じ深さで扱わない。

## 診断の観点

1. **モデル**: 指示遵守を優先するならv6を基準にする。v6-wildは公式にも探索的・予測しにくいモデルと説明されるため、逸脱を即座にバグと断定しない。v6-miniは高速案出し向けで、v6との差分は未確認。
2. **設定**: VarietyがStyleを書き換える設定になっていないか、Vocal Gender、Persona、Inspo、Exclude Styles、Max Modeの有無を確認する。
3. **責務分離**: Styleに全体音像、Lyricsに本文と局所cueが置かれているかを短く確認する。
4. **競合**: 複数ジャンル、複数BPM、相反するムード、include/excludeの同時指定を減らす。ただし、症状報告後は競合確認だけを先に要求しない。
5. **タグ固有の確認**: Lyricsタグの問題では、問題になったタグだけを[tags.md](tags.md)と`tag-catalog.json`で確認する。公式旧世代参照でもv6固定コマンドとは限らず、コミュニティcueでも直ちに無効とは断定しない。
6. **編成分岐**: 音域や厚みの相談で編成が不明なら、[arrangement-diagnosis.md](arrangement-diagnosis.md) の候補を提示し、選択を受ける。
7. **再指示**: 選択された編成に沿って主役を1〜2個に絞り、`instrument + action + role` へ具体化する。
8. **局所修正**: 全体を作り直すより、必要ならReplace SectionやExtendを使う。
9. **試聴確認**: ジャンル、声、楽器、構造、歌詞の実現は音声を聴いて判定する。テキストvalidatorは結果音声を判定できない。

## 代表的な失敗モード

| 症状 | 対応 |
| --- | --- |
| ジャンルが汎用ポップ化する | v6へ戻す、Varietyを0にする、主ジャンル1つ＋補助要素2〜3個へ整理する。これは設定部分以外は暫定仮説。 |
| 指定楽器が出ない | `instrument + action + role` にする。例: `active melodic bassline following guitar riffs`。主役楽器を1〜2個に絞る。 |
| 不要な楽器が混ざる | Styleの列挙を減らし、Exclude Stylesが使える場合だけ短い除外語を試す。結果保証ではない。 |
| 声の性別・質感が違う | CustomのVocal Genderを設定し、Styleには音域・質感・発音を追加する。Persona/Inspoとの競合も確認する。 |
| 構造タグが無視される | 問題のタグだけを確認する。`[Verse]`等の公式旧世代参照、`[Drop]`等のコミュニティcue、未知タグ、タグが独立行でないケースを区別する。そのうえで非公式cueと長い角括弧指示を減らし、必要ならReplace Section。 |
| Chorusを先頭にしてもイントロが付く | 既にLyricsが`[Chorus]`始まりなら、それを再確認させるだけで終わらせない。Styleに`cold open with the chorus hook, lead vocal starts on beat one, full-band entrance`など肯定的な開始指示を加え、v6・Variety 0で比較する。念のため`[Intro]`、冒頭のinstrumental cue、長いビルド指示がないかだけ確認する。 |
| Lyricsが途中で切れる・反復する | 不要な説明と重複を削り、構造を単純化する。長尺はExtend等を検討する。上限内でも歌唱完了は保証されない。 |
| Instrumentalなのに声が入る | Lyrics本文を空にし、Instrumental設定を確認する。否定文だけでの回避は保証しない。 |
| BPM・テンポが守られない | BPMを1つに絞り、相反するtempo語を削る。実テンポは試聴で確認する。 |
| J-Rockで中域が薄い | 編成が不明なまま`midrange`だけを足さない。ギター中域、ボーカル/スネア、鍵盤/パッドの候補から選択してもらい、選択後にStyleを確定する。詳細は`arrangement-diagnosis.md`。 |
| Rockで低音が少なく薄い | `deep bass`だけで決め打ちせず、ベースギター主体、キック/ドラム主体、低中域ギター主体、サブシンセ補強の候補を比較する。自然なRockか現代的な低域かも確認する。 |

## 公式情報と仮説の境界

公式に確認できる操作・設定は、v6のモデル特性、Variety、Vocal Gender、Max Mode、Replace Section、Extend、Exclude Stylesなど。これらも生成結果を保証するものではない。

次はコミュニティ仮説または未確認事項として扱う。

- 「短いStyleほど必ず良い」
- 否定文が必ず逆効果になる
- 特定の語句で楽器が必ず出る
- StyleとLyricsのどちらかが常に優先される
- `[End]`、`[Hard Stop]`、`[Guitar Solo]`等が公式固定コマンドである
- `midrange` や `deep bass` という語だけで、特定の楽器編成や周波数バランスが必ず実現する
