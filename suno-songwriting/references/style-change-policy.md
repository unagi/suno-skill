# Style変更ポリシー

Styleの改善は、語句を足し続ける作業ではなく、最後に承認されたStyleを基準にした変更管理として扱う。音楽では、音圧、音域、密度、編成、明瞭度、ジャンルらしさが同じ音響資源を取り合うため、目的だけを達成しても既存の意図を壊す変更は採用しない。

## 最初の質問

ユーザーが既存Styleの改善を求め、現在のStyle全文を提示していない場合、最初に次だけを聞く。

```text
現在使っているStyle全文を、変更せずそのまま貼ってください。
```

Styleがない状態では、具体的な修正Styleを作らない。ジャンルや症状から一般的な候補を説明することはできるが、既存Styleとのマッチングや副作用判定は行わない。

Style全文を受け取ったら、必要に応じてモデル、Variety、生成結果の症状を確認する。Lyricsやタグは、症状に関係する場合だけ追加で確認し、最初から全入力を要求しない。

基準版と候補の比較、文字数や構文の検証は、意味解釈とは別の付属品質ゲートへ委ねる。LLMは候補を手計算で通したり、ゲートの判定規則を再現したりせず、候補の最終化時に実行手順を呼び出す。ゲート未実行時は検証済みの候補として提示しない。

## 変更契約

Style修正では、会話中に次の状態を保持する。JSON化する場合の正本は次の形とする。

```json
{
  "baseline": {
    "id": "accepted-001",
    "status": "accepted",
    "style": "現在使っているStyle全文",
    "model": "v6",
    "settings": { "variety": 0 },
    "accepted_observations": ["ジャンル感は維持できている"]
  },
  "intent": {
    "verbatim_request": "低音を増やしたい",
    "normalized_goal": "低域の重量感を増やす",
    "priority": "must",
    "origin": "user_explicit"
  },
  "preserve": ["J-Rock", "lead vocal"],
  "constraints": ["ジャンルをRockから外さない"],
  "acceptable_side_effects": [],
  "proposal": {
    "hypothesis": "ベースギターの土台が不足している",
    "exact_operations": [
      { "type": "append", "text": "clearly audible electric bass locked with the kick", "tradeoff_ids": ["electric-bass-foundation"], "impact": "high" }
    ],
    "expected_effects": ["低域の土台とキックとの接着を増やす"],
    "risks": ["キックとのマスキング", "ベースが前に出すぎる"],
    "affected_dimensions": ["spectral.low", "arrangement.roles"],
    "confirmation_state": "pending"
  }
}
```

## 判断手順

### 1. 基準版を固定する

- 最後にユーザーが承認したStyleを`baseline`とする。
- 未採用、却下、試行中の候補を次の基準版にしない。
- 基準版からの差分を作り、直前候補へ修正を継ぎ足さない。

### 2. 要望を目的へ翻訳する

ユーザーの発言は、原文と解釈を分ける。

- `verbatim_request`: ユーザーの言葉を保持する
- `normalized_goal`: 何を改善したいかの仮説
- `preserve`: 変えたくないと明示されたもの、および基準版から保護するもの
- `constraints`: ジャンル、声、主要楽器、自然な音像などの制約
- `acceptable_side_effects`: ユーザーが許容した代償

`preserve` と `constraints` は空にせず、少なくとも1つずつ明示する。候補を比較している間は `confirmation_state: "pending"`、ユーザーが案を選び最終Styleの適用を許可した後だけ `"confirmed"` とする。低影響の語句変更でも、この選択順序を省略しない。

「音圧」「厚み」「低音」「迫力」は一つの意味に決め打ちしない。瞬発的なパンチ、持続的な厚み、知覚上の平均音量、低域重量、同時発音数による密度などに分け、維持事項を壊す可能性がある場合だけ一問確認する。

### 3. 影響分析を先に行う

候補を出す前に、現在のStyleがすでに何をしているかを短く整理する。

- ジャンル・サブジャンル
- 主役の楽器と土台
- ボーカルの位置
- 低域、中域、高域の役割
- 密度、空間、ダイナミクス
- 追加変更が奪う可能性のある要素

候補ごとに、変更断片、狙う効果、影響軸、副作用、ジャンル上の自然さ、元に戻す条件を示す。

### 4. 候補を比較する

通常は最大3案とし、次のように役割を分ける。

- **案A: 保守案** — 既存編成を維持し、最小の変更で目的へ近づける
- **案B: 別の音楽的役割を使う案** — 同じ目的を別の楽器・奏法で実現する
- **案C: 積極案** — ジャンルや音像を少し動かす代わりに効果を強める

各案に「何を変えるか」「何を変えないか」「副作用」「どんな場合に近いか」を添え、ユーザーに最も近い案または「どれでもない」を選んでもらう。

### 5. 高影響変更は確認を取る

次の変更は、ユーザーが選択するまで最終Styleへ確定しない。

- 新しい楽器、ボーカル役割、編成方式の追加
- アコースティックと電子的編成の切り替え
- ジャンル中心や時代感の変更
- 主旋律と伴奏の前後関係の変更
- ダイナミクスや音圧感を大きく変える圧縮・飽和・密度の提案

### 6. 確定案と検証

選択後に、基準版からの変更だけを反映した貼り付け用Styleを出す。必ず次を併記する。

- 変更した点
- 変更していない点
- 想定した副作用
- ユーザーが選択・許容した副作用
- 比較時に固定するモデル・設定
- 試聴で確認する項目

生成後の結果は、目的達成、既存意図の回帰、新しい副作用、生成ばらつきで判定不能に分類する。回帰や副作用が出たら、直前候補へ反対語を足すのではなく、基準版へ戻って次の仮説を一つだけ試す。

## 役割分担

- LLM: ユーザー意図の解釈、音楽的仮説、候補比較、質問
- 知識JSON: 楽器・編成・トレードオフの事前分布
- validator: 基準版との一致、宣言済み差分、保護語、高影響変更の確認状態
- 試聴: 実際の音圧、EQ、ジャンル適合、楽器の可聴性、歌唱結果

Style文だけからLUFS、Hz、dB、実際のミックス結果を保証しない。
