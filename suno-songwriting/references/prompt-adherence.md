# 指示違反への診断と再指示

Sunoの生成結果が指示から外れたとき、「モデルが無視した」とだけ結論づけず、入力・設定・モデル特性・生成結果を分けて診断する。

## Cover・Voice・Extend・Studioの機能境界

次の表は、操作そのものと、生成結果に期待してよいことを混同しないための基準である。日付は最終確認日であり、Sunoの画面・モデル更新時は再確認する。

| 機能 | 根拠状態・最終確認・適用条件 | 記載できる操作範囲 | 回答で保証・推論してはいけないこと |
| --- | --- | --- | --- |
| Cover | `documented` — `official.help.v6.whats-new`（2026-09-14確認、v6の編集群）と `official.help.cover`（2026-09-14確認、個別手順は2024年）。 | 自分のライブラリ内の曲を、メロディを保ちながら別のStyleへ変換する機能として案内されている。 | メロディ、編曲、声が曲の全区間で不変になること。Cover結果の参照条件が後続の編集にも再適用されること。 |
| Voice | Voiceプロフィールの作成・Create選択は `documented` — `official.help.voice`（2026-09-14確認、2026-05更新）。モデル互換性は `conflict` — `official.help.voice-faq`（2026-03更新、New Voicesはv5.5のみ）を現行v6へ継承しない。Coverとの初回併用は `user_confirmed`（この案件のみ、公式の直接根拠は未確認）。 | 本人確認済みの自分のVoiceをCreateで選ぶ。ユーザーが指定した対象画面では、初回CoverでVoiceと併用する。 | Voiceの完全な同一性、複数Voiceの区間別指定、再生成後のVoice参照の維持、またはCoverとの併用を他のモデル・画面でも保証すること。 |
| Extend | `documented` — `official.help.extend`（2026-09-14確認、2025-12更新）と `official.help.v6.whats-new`（v6の編集群）。 | 元トラックの残す位置を選び、そこから新しいLyricsやStyle詳細で末尾を作る。`Get Whole Song`は新しい末尾を元トラックへつなぐ。 | Cover元の音源・メロディ参照や選択Voiceが、延長区間で再アンカーされること。別々に生成した2曲を横方向に結合すること。 |
| Replace Section | `documented` — `official.help.replace-section`（2026-09-14確認、2025-12更新）と `official.help.v6.whats-new`（v6の編集群）。 | 既存曲の一部を置換し、候補からWhole Songを作る局所編集。 | 原曲・Voice・Cover参照を再アンカーする機能、または局所編集後の厳密な構成・声の維持。 |
| Studio | `documented` — `official.help.studio-2`（2026-09-14確認、Studio 2.0／Premier）。 | タイムライン上で、ステムの分離・編集・配置、音量・ピッチ等の調整を行える。これはSuno内の編集工程である。 | Studioの編集・ステム操作が、Cover/Voice参照を保った再生成や、別々のCover生成物を一曲として再アンカーする手段になること。 |

「Cover結果をExtendできる」ことと、「Coverの参照がExtendへ引き継がれる」ことは別である。前者はExtendの元トラックを選んで末尾をつなぐ操作として文書化されているが、後者を保証する公式記述は確認できない。したがって、CoverとExtendをUI上の排他的機能と断定せず、**Cover参照を保った延長の方法としては提案しない**。

Suno内の回答では、Cover結果を後半だけ別Coverで再生成する、Extend/Replace Sectionを再アンカーとして使う、別作品由来のステムを組み合わせて参照維持を取り戻す、といった**再生成を含む**工程を、根拠なしに確実な解決策として提示しない。現行公式情報、または条件が一致する `observed` な事例が根拠になる場合は、その確度・時期・適用条件を添えて案内できる。Studioで既存結果のステムを編集すること自体は有効な別工程だが、参照が外れた再生成を自動的に救済するとは扱わない。

### 参照維持が崩れる相談

CoverのメロディとVoiceの両方が後半で変わったという報告は、`observed`（当該生成の観測）として受け取る。コミュニティ記録 `community.reddit.cover-voice-consistency.2026-04` はV5/V5.5期の非統制な失敗観測であり、v6の仕様・発生率・原因には使わない。内部で「両参照が同時に薄れる」などの因果を推測しない。

この種の課題は、次の順で回答する。

1. まず対象モデル・画面・更新時期の現行公式情報を確認する。公式に解消手段や対応範囲が明記されていれば、その条件付きで肯定的に案内する。
2. 公式に直接の説明がなければ、同じモデル・画面・時期を特定できるコミュニティ記録やユーザー事例を探す。複数の一致事例があれば、`observed` と明示して実用上の選択肢として案内してよい。
3. 公式情報と観測が食い違う、または鮮度が不足する場合は、`conflict` または「要確認」とし、確実な解決策とは表現しない。
4. 既存の「再生成を解決策にしない」は、Cover参照の維持を求める今回の観測・条件に対するガードレールである。将来の現行公式情報、または十分に条件がそろった観測が再生成での維持・回復を示すなら、根拠種別と条件を明記して肯定的に案内できる。

1. 使用モデル、Cover元、選択Voice、Style/Lyrics、編集種別（Cover/Extend/Replace Section）、崩れ始める位置を確認する。
2. Coverのメロディ表現とVoiceを同時に求める場合は、初回Coverで両方を設定する。再生成で両参照を維持・回復できるかは、現行公式情報と条件が一致する観測で確認し、根拠がなければ未確認と明記する。
3. その初回Coverの少数の生成を比較し、メロディとVoiceを試聴する。既に参照が外れた結果には、現行の裏付けがないExtend、Replace Section、別Coverを後半へつなぐ方法を確実な解決策として勧めない。
4. 必要なら、成立しているCover結果をStudioでステム編集する選択肢だけを示す。Studioの編集は既存音声を扱う工程であり、再生成した区間の参照を戻すものではない。
5. 目標を満たせなければ、「Cover参照を保った再生成手段は確認できない」と明記して止める。未依頼の外部ツールや2曲結合へ話を広げない。

## 症状が報告された後の応答原則

ユーザーが「既にサビ始まりを指定しているのにイントロが付く」「Rockを指定しているのに低音が薄い」と報告した場合、入力ミスだけに還元せず、生成後の症状に対する有益な改善へ進む。ただし、既存Styleの改善では、Style全文がない限り具体的な修正版を先に返さない。Style全文があれば変更契約を先に適用し、Lyrics全体やすべてのタグを妥当と仮定してはいけない。症状ごとに、確認の明快さと結果への影響で切り分けの深さを変える。

### 既存Styleを直すときの順序

既存Styleの改善では、回答の価値は「すぐ別のStyleを返すこと」ではなく、現在の音像と変更のトレードオフを可視化して、ユーザーが意図に近い変更を選べることにある。詳細な契約は [style-change-policy.md](style-change-policy.md) に従う。

1. Style全文が未提示なら、最初に `現在使っているStyle全文を、変更せずそのまま貼ってください。` と尋ねる。短い抜粋や要約から、完成版のStyleを推測して返さない。
2. Style全文がある場合は、それを基準版として、現在の編成・音域・音像、ユーザーの観測症状、達成したい目的、維持したい要素を分ける。ユーザーの「低音を増やす」「中音を埋める」などの表現を、そのまま追加操作にしない。
3. 現在のStyleから予想される副作用を先に説明する。たとえばベース追加は低域の土台を増やす一方、キックやギターとの分離を損なう可能性があり、パッド追加は持続感を増やす一方、ボーカルやギターの明瞭度を下げる可能性がある。
4. 通常は、保守的な案、別の役割で目的を満たす案、必要なら強い案の2〜3案を提示する。各案で変更するもの・維持するもの・副作用・向いているケースを示し、「どれが一番近いですか？」と選択を求める。
5. 選択後だけ、基準版との差分が宣言された最終Styleを出す。生成後に悪化した場合は、前のStyleへ戻ってから別の主仮説を試し、前案へ対策語を継ぎ足して複雑化しない。

| 確認の種類 | 例 | 応答での扱い |
| --- | --- | --- |
| 明快で低コスト | サビ始まりなのにイントロが付く場合、`[Chorus]`より前に`[Intro]`、本文、instrumental cueがないか | 本質的な対策を示した後に、一文で確認する。Lyrics全体の監査へ広げない。 |
| タグ固有の確認 | `[Verse 1]`、`[Drop]`、長い角括弧指示など | そのタグだけを台帳で分類し、公式旧世代参照・コミュニティcue・未知・配置不備を確認する。妥当とも無効とも一括断定しない。 |
| 音楽的な診断 | 中域不足、低音不足、音が薄い | 楽器編成や役割を複数仮説に分け、単一のStyleを決め打ちしない。 |

Style全文があり、変更契約の対象になる場合の基本順序は次のとおり。

1. まず現在のStyleから、症状と関係する編成・音域・音像を読み取る。
2. 次に、結果を変えうる確認を症状に必要な範囲だけ添え、維持条件を確認する。
3. 音域や厚みの問題で編成が不明なら、2〜3案を提示する。各案には「何を前に出すか」「どの音楽的役割を追加するか」「どんな場合に近いか」「どんな副作用があるか」を添える。
4. ユーザーが案を選ぶか「その他」を示した後に、貼り付け用Styleを確定する。

確認を省略しないが、確認だけで回答を終えない。電源コードの確認は一文で済む場合があり、回路設計の説明が必要な場合まで同じ深さで扱わない。

## 診断の観点

1. **モデル**: 指示遵守を優先するならv6を基準にする。v6-wildは公式にも探索的・予測しにくいモデルと説明されるため、逸脱を即座にバグと断定しない。v6-miniは高速案出し向けで、v6との差分は未確認。
2. **設定**: VarietyがStyleを書き換える設定になっていないか、Vocal Gender、Persona、Inspo、Exclude Styles、Max Modeの有無を確認する。
3. **責務分離**: Styleに全体音像、Lyricsに本文と局所cueが置かれているかを短く確認する。
4. **競合**: 複数ジャンル、複数BPM、相反するムード、include/excludeの同時指定を減らす。ただし、症状報告後は競合確認だけを先に要求しない。
5. **タグ固有の確認**: Lyricsタグの問題では、問題になったタグだけを[tags.md](tags.md)と`tag-catalog.json`で確認する。公式旧世代参照でもv6固定コマンドとは限らず、コミュニティcueでも直ちに無効とは断定しない。
6. **編成分岐**: 音域や厚みの相談で編成が不明なら、[arrangement-diagnosis.md](arrangement-diagnosis.md) の候補を提示し、選択を受ける。
7. **再指示**: 選択された編成に沿って主役を1〜2個に絞り、`instrument + action + role` へ具体化する。
8. **局所修正**: LyricsやStyleの局所的な問題ならReplace SectionやExtendを検討する。ただし、Coverメロディ・Voiceの保持を再アンカーする手段としては扱わない。
9. **試聴確認**: ジャンル、声、楽器、構造、歌詞の実現は音声を聴いて判定する。テキストvalidatorは結果音声を判定できない。

## 代表的な失敗モード

| 症状 | 対応 |
| --- | --- |
| ジャンルが汎用ポップ化する | v6へ戻す、Varietyを0にする、主ジャンル1つ＋補助要素2〜3個へ整理する。これは設定部分以外は暫定仮説。 |
| 指定楽器が出ない | `instrument + action + role` にする。例: `active melodic bassline following guitar riffs`。主役楽器を1〜2個に絞る。 |
| 不要な楽器が混ざる | Styleの列挙を減らし、Exclude Stylesが使える場合だけ短い除外語を試す。結果保証ではない。 |
| 声の性別・質感が違う | CustomのVocal Genderを設定し、Styleには音域・質感・発音を追加する。Persona/Inspoとの競合も確認する。 |
| 構造タグが無視される | 問題のタグだけを確認する。`[Verse]`等の公式旧世代参照、`[Drop]`等のコミュニティcue、未知タグ、タグが独立行でないケースを区別する。そのうえで非公式cueと長い角括弧指示を減らし、必要ならReplace Section。 |
| Chorusを先頭にしてもイントロが付く | 既にLyricsが`[Chorus]`始まりなら、それを再確認させるだけで終わらせない。Styleに`cold open with the chorus hook, lead vocal starts on beat one, full-band entrance`など肯定的な開始指示を加え、v6・Variety 0で比較する。念のため`[Intro]`、冒頭のinstrumental cue、長いビルド指示がないかだけ確認する。 |
| Lyricsが途中で切れる・反復する | 不要な説明と重複を削り、構造を単純化する。続きのLyrics/Styleを作る目的ならExtendを検討するが、CoverやVoiceの参照維持は保証しない。上限内でも歌唱完了は保証されない。 |
| Instrumentalなのに声が入る | Lyrics本文を空にし、Instrumental設定を確認する。否定文だけでの回避は保証しない。 |
| BPM・テンポが守られない | BPMを1つに絞り、相反するtempo語を削る。実テンポは試聴で確認する。 |
| J-Rockで中域が薄い | 編成が不明なまま`midrange`だけを足さない。ギター中域、ボーカル/スネア、鍵盤/パッドの候補から選択してもらい、選択後にStyleを確定する。詳細は`arrangement-diagnosis.md`。 |
| Rockで低音が少なく薄い | `deep bass`だけで決め打ちせず、ベースギター主体、キック/ドラム主体、低中域ギター主体、サブシンセ補強の候補を比較する。自然なRockか現代的な低域かも確認する。 |

## 公式情報と仮説の境界

公式に確認できる操作・設定は、v6のモデル特性、Variety、Vocal Gender、Max Mode、Cover、Replace Section、Extend、Exclude Stylesなど。これらも生成結果を保証するものではない。

次はコミュニティ仮説または未確認事項として扱う。

- 「短いStyleほど必ず良い」
- 否定文が必ず逆効果になる
- 特定の語句で楽器が必ず出る
- StyleとLyricsのどちらかが常に優先される
- `[End]`、`[Hard Stop]`、`[Guitar Solo]`等が公式固定コマンドである
- `midrange` や `deep bass` という語だけで、特定の楽器編成や周波数バランスが必ず実現する
- ExtendがCover元のメロディ参照または選択Voiceを再アンカーする
- Replace SectionがCover・Voiceの維持問題を解決する
- Studioのステム編集がCover/Voice参照を保つ再生成の代替になる
